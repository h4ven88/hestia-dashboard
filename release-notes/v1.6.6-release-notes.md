# Hestia v1.6.6 Release Notes

**Release Date:** 2026-09-12

---

## Please update, even if Hestia looks fine

This release fixes the mechanism that delivers updates to you. If you have been running Hestia from your own hub rather than from hestari.com, there is a good chance you have not received any fixes since 2026-09-09 and had no way to know.

---

## What went wrong

Hestia reaches your hub through Hubitat Package Manager, which decides an update exists purely by comparing a version string in the project's package manifest against what you have installed. That manifest was accidentally left at 1.6.4 when v1.6.5 shipped, so **HPM told everyone they were up to date for three days.**

That silence spread further than HPM. The companion app only re-downloads the dashboard file to your hub when the app itself is installed or upgraded. No update signal meant no upgrade, which meant the `index.html` served from your hub at `/local/` stayed frozen on whatever version you last installed. Only people loading hestari.com kept receiving fixes, because that is served directly from the project's main branch.

The practical result: several people reported bugs that had already been fixed, against code they had no way to update.

## Two more breaks found while fixing that one

Investigating the above turned up two older bugs in the same chain, both of which had been quietly defeating automatic dashboard updates for much longer.

- **The version check could never match.** After downloading the dashboard, the companion app read the version back out of the file to record what it had installed. The pattern it used only recognized single quotes, but the published file is minified and uses double quotes. So it never matched, and the app fell back to recording its own version instead. That made the update comparison meaningless, and in the wrong circumstances would have caused every hub to re-download the full 600 KB dashboard on every check, indefinitely.
- **The update check never ran at all.** The request that asks "is there a newer dashboard?" did not tell GitHub what format it expected, and GitHub serves that file as plain text. The response therefore failed to parse, the error was swallowed, and the check quietly gave up every time. This means automatic dashboard updates likely never worked, and only the manual "Update Dashboard" button ever did.

## What is fixed

- Both bugs above are fixed, so the update check now actually runs and actually compares the right things.
- **The companion app now re-checks every 3 hours**, so your hub's dashboard file keeps itself current instead of only updating when the app is reinstalled. This is the real safety net: even if the manifest is ever wrong again, hubs recover on their own within hours.
- **Hestia now tells you on screen when something on your hub is out of date**, instead of hiding that in Settings → Diagnostics where you would only find it if you were already troubleshooting. It distinguishes three cases and gives the correct instruction for each: the companion app being behind, the dashboard file on your hub being behind, and this device loading an older copy than your hub has.
- The existing "new version available" banner now tells you *how* to update when you are loading from your hub, rather than only announcing that a version exists.
- Diagnostics no longer tells you to update a companion app that is already newer than your dashboard.

## Hub log flooding fixed properly

Some users saw their Hubitat log filling with `Received local request for App <id> that does not exist`. That happens when the Hestia companion app gets reinstalled and receives a new app ID, leaving the dashboard holding the old one. From hestari.com there is no way to look up the new ID automatically, so it kept retrying the dead one every 30 seconds, roughly 2,880 log lines a day.

An earlier attempt at this fix discarded the stored credentials whenever the hub returned "not found." That turned out not to work at all in the situation that matters, because of how browsers handle cross-origin requests: when the app ID is dead, the browser blocks the response entirely and the dashboard cannot tell the difference between "that app is gone" and "your hub is unreachable right now." Discarding on a signal that ambiguous risked wiping working credentials over a brief Wi-Fi drop, with no way to recover without walking over to the hub.

Hestia now backs off instead of discarding. After a few consecutive failures it stops issuing the requests entirely and retries progressively less often, down to about 48 quiet attempts a day rather than 2,880 noisy ones, and it resumes normally on its own the moment the hub answers again. Your credentials are never thrown away on a guess. Two related improvements came with it: if another device in your home has already seen the new app ID, this one now picks it up automatically through cloud sync rather than staying stuck, and Settings → Diagnostics now tells you plainly when Hestia has backed off and what to do about it, instead of just reporting "Unreachable."

## Notes

- **This release includes Groovy changes.** Update via Hubitat Package Manager, or re-paste `HestiaDashboard.groovy` under Apps Code, then **open the Hestia app on your hub and click Done**. That last step is what refreshes the dashboard file on your hub.
- The 3-hour self-check only helps once you are on v1.6.6 or later. It protects future releases, not this one, which is why this update has to be taken manually.
- If HPM still does not show an update, use its Repair option, which re-downloads regardless of version.
