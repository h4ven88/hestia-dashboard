# Hestia v2.1.1 Release Notes

**Release Date:** 2026-09-30

A same-day fix for v2.1.0. If you created a reminder in the evening, it went in on the wrong day.

---

## "Today" meant the wrong day for part of every day

Every place the dashboard wrote down a date used the UTC date rather than your local one. Those are the same for most of the day and different for the rest: west of UTC they diverge all evening, east of UTC all early morning.

In New York, from 8 PM onward, "today" silently became tomorrow.

**What that looked like.** Choosing **Once (today)** at 8:35 PM stored the reminder for the following day. The list then correctly said "Tomorrow at 8:35 PM", so the display was right and the stored date was wrong, which made it read as the app arguing with itself.

**And in the other direction.** A reminder created at 8:42 PM disappeared from *today's* calendar row. Its creation time was reduced to a UTC day and read back as UTC midnight, which is 8 PM the previous evening in New York, so today looked like it came before the reminder existed.

Both are fixed, along with the same mistake in the reminder date picker, the calendar's own day cells, and the date Athena is given when you set a reminder by voice.

**The calendar squares were wrong east of UTC too.** A one-time reminder was drawn on the day before its own, everywhere ahead of UTC. New York never showed it, which is why it survived the original release.

---

## The calendar form now refuses a schedule that cannot fire

v2.1.0 added that refusal to Settings → Reminders and missed the inline **Add Reminder** form on the home screen. It could not be reached there anyway, because "today" was always tomorrow and therefore always in the future. Fixing the date is what makes a genuinely past time possible, so the guard had to land in the same release.

Pick a time that has already gone by today and it now says so instead of saving something that will never happen.

---

## Reminders that have run out say Finished

A repeat whose end date has passed, or a one-time that has been and gone, used to sit under **Active Reminders** reading "No upcoming fire" — a state with no name and nothing to do about it.

They now appear under **Finished**, below the active ones. Edit gives one a new schedule; Delete removes it. Nothing is deleted for you.

A reminder you switched **off** is paused, not finished, and stays in the active list where you can switch it back on.

---

## What you need to do

**Recurring reminders fix themselves.** The hub's queue is recomputed from scratch each time the dashboard syncs, so a daily or weekly reminder is correct as soon as you load this build.

**A one-time reminder created during an evening is still stored a day late.** Its date is saved, and only you know whether you meant that day, so Hestia will not rewrite it. Open Settings → Reminders, hit **Edit**, and set the date you wanted.

---

## Updating

1. **Companion app.** HPM, or paste `HestiaDashboard.groovy` over Apps Code → Hestia Dashboard and Save. The Groovy is unchanged in this release; its version moves with the dashboard so the two never look out of step.
2. **Open the Hestia app and click ⬇ Update Dashboard File.**
3. **The dashboard.** On hestari.com, reload. Served from your hub, it arrives at step 2.
4. **Check it.** The footer should read v2.1.1.

---

## For the technically inclined

One helper, `_localDateStr(date, zone)`, now answers "what calendar day is this instant on, in this zone", and every producer of a date string goes through it. It uses `Intl` rather than `getDate()` and friends because it has to be able to answer for the zone stored on the reminder, not only the browser's own.

The recurrence engine itself was never wrong. `computeNextFire()` has been zone-correct since the DST work, and is tested across both hemispheres. The bug was entirely in the callers that produced the date strings it was handed, and in the calendar's own filters — which is why every reminder fired at the right *time*, just occasionally on the wrong *day*.

471 tests, and seven deliberate breaks of the new code, each restoring the exact line v2.1.0 shipped, all caught. One of those breaks survived the first sweep: the calendar day-cell test passed against the broken line because New York's local midnight happens to share a UTC date. It only bites east of UTC, so that check now runs in a child process with the zone set to Tokyo.
