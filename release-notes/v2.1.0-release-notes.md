# Hestia v2.1.0 Release Notes

**Release Date:** 2026-09-29

---

## Reminders now happen without you watching

Until this release, a reminder only fired if a dashboard was open at that exact moment. Closed overnight, tablet asleep, hub rebooted, browser tab shut: the reminder simply did not happen, and nothing ever told you.

That is the worst way for a reminder to fail. You asked to be reminded, you were not, and you only find out by noticing the thing you were meant to do.

**Your hub fires them now.** It is always on, so a reminder arrives whether or not anything is open, as a notification on your phone.

---

## What you will see

**A reminder that fires while you are looking at a screen** speaks and shows a banner, as before.

**A reminder that fires while nothing is open** arrives as a push notification, and is waiting in Settings → Reminders when you next look.

**Each reminder shows its own state.** Not read, Read, or Missed, with the time it was scheduled for. "Mark as read" clears it. Acknowledging on one device clears it on all of them within seconds, rather than on the slower settings sync.

**Missed means missed.** If fifteen minutes pass without you acknowledging, it is marked missed and stays that way; reading it later does not pretend you caught it. Nothing ever alerts twice for the same occurrence, which is what stops this becoming a snooze that will not shut off.

**The board clears each morning.** No history is kept and none is wanted: a dashboard closed for three days says "missed", it does not enumerate Monday, Tuesday and Wednesday. One-time reminders are the exception and stay for a week, because they do not come round again.

---

## You can finally edit a reminder

Previously a typo in a label, or a daily reminder set to the wrong time, could only be fixed by deleting it and creating it again. Every reminder now has an **Edit** control that opens the whole thing prefilled, day selections and end date included.

Editing a one-time reminder that has already fired re-arms it, since changing its time plainly means you want it again. A reminder **you** switched off stays off.

---

## Reminders that could never fire now say so

The form defaults to today's date and 08:00, which is a past-time combination for most of the day. Saving that stored a reminder that scheduled nothing and displayed the same "No upcoming fire" as one that had legitimately finished. It looked fine and did nothing.

Now a schedule that can never fire is **refused at the point you save it**, and an existing one says **"Time has passed"** rather than leaving you guessing. If you have a reminder that has quietly never worked, this is likely why, and Edit will fix it.

A related display bug is gone too: "Today" and "Tomorrow" were worked out from elapsed time rather than the calendar, so a reminder due tomorrow at 09:44, read at 09:46 today, was 23 hours and 58 minutes away and therefore labelled **"Today at 9:44 AM"**. It said today and meant tomorrow, on most daily reminders, for most of the day.

## Also

**The dashboard version now shows in the footer**, next to the copyright, so you can tell at a glance what a device is running without opening Diagnostics.

**Reminders ignore your alarm state.** They are not security events. A device set to "armed only" for push would otherwise have swallowed every reminder while you were out, which is exactly when you are least likely to be looking at a screen.

## Updating

1. **Companion app.** HPM, or paste `HestiaDashboard.groovy` over Apps Code → Hestia Dashboard and Save. **This release does change the app**, so it is required.
2. **Open the Hestia app and click ⬇ Update Dashboard File.**
3. **The dashboard.** On hestari.com, reload. Served from your hub, it arrives at step 2.
4. **Check it.** Settings → Diagnostics → Run all checks. Companion App should read green "v2.1.0 (up to date)".

**Push needs to be working**, since that is how a reminder reaches you when nothing is open. If Diagnostics shows Push Pipeline amber with `Permission: default`, open Settings → Push Notifications and use **Re-enable notifications**.

**Households with no companion app** keep the old behaviour: reminders fire only while a dashboard is open. The hub is what makes the rest possible, and there is no hub-side component without the app.

## For the technically inclined

The hub does no date arithmetic. The dashboard precomputes absolute UTC instants into each reminder and the hub only compares numbers, so weekday sets, month lengths, end dates and daylight saving all stay in the one implementation that is tested across both hemispheres. Hubitat's own DST behaviour in `schedule()` is undocumented, and a second implementation would have been a second chance to get it wrong.

One scanning job, never one per reminder: the platform caps an app at 75 scheduled jobs. The tick is cheap when nothing is due and only writes when something changed.

Runtime state lives in its own `state` key, never inside the config blob, because marking occurrences there would mean re-uploading an entire household config every minute against a store with a documented truncation history. Acknowledgements go straight to the hub over a new endpoint rather than through settings sync, which is what makes cross-device clearing take seconds instead of a minute, and removes a last-write-wins race that could silently lose one.

Reboots do not lose reminders. Hubitat keeps scheduled jobs across a restart; what it drops is a fire time that elapses while the hub is down, and a `systemStart` handler reconciles exactly that window. An occurrence too old to be worth interrupting for is recorded as missed rather than fired, because a hub returning after three days and announcing everything it missed would be worse than silence.

Verified with 434 tests and four mutation sweeps in which all 28 deliberate breaks were caught. The Groovy half has no execution environment anywhere in the toolchain and was reviewed against Hubitat's documentation rather than run.
