# Hestia v2.1.3 Release Notes

**Release Date:** 2026-09-30

Recovering a device that has lost your household key now works without you assembling anything by hand.

---

## The recovery screen builds the link for you

v2.1.2 added a field for entering your household key, and told you where to find it: open `hestia-token.json` on your hub, take `appId` and `token` from it, and open `/apps/api/<appId>/config?access_token=<token>`.

That instruction was incomplete, and the first person to follow it hit the gap. **`hestia-token.json` contains four credentials, not two:**

```
appId / token                  ← the Hestia companion app
makerApiAppId / makerApiToken  ← Maker API
```

Take the wrong pair and you get a blank page, with nothing to tell you which of the two mistakes you made.

**The screen now does it for you.** Paste the whole of `hestia-token.json` into the first box, press **Build my link**, and open the link it gives you. It picks the right pair, works out your hub's address from the file itself, and refuses a paste that only contains the Maker API fields instead of quietly producing a link that cannot work.

It also says what a blank result means: if that page is empty or shows `null`, your hub has no saved settings, and starting fresh is the right move rather than hunting for a key that is not there.

---

## Diagnostics was still giving the impossible advice

v2.1.2 rewrote the recovery guidance on the lockout screen, because "open Hestia on a device that is already working" cannot be followed by the households that need it — if any device still worked, they would not be reading that message.

**The same wording existed in Settings → Diagnostics and was missed.** So the Cloud Sync check went on telling people to use a device they do not have. Now fixed to match, naming the path that needs no second device.

**And it was hiding the most useful thing it knew.** If your settings could not be read, Diagnostics reported only that, and said nothing about whether your *saves* were also being rejected. Those are different problems with different fixes, and the message that distinguishes them was already being recorded internally and simply not shown. A rejected save now appears alongside.

That matters for one case in particular: a household that sets itself up fresh over its own existing record is authorised by the Maker API token stored in that record. Entering a **newly generated** token instead of the one you already had is refused, so the setup completes locally and never reaches your other devices. Repeating it changes nothing, and until now nothing said why.

---

## Updating

1. **The dashboard.** On hestari.com, reload. That is all this release changes.
2. **Companion app.** Paste `HestiaDashboard.groovy` over Apps Code → Save, then open the Hestia app and click **⬇ Update Dashboard File** to pull the new dashboard to your hub.
3. **Clicking Done is not required this time.** The companion app's code is byte-for-byte unchanged in this release; its version number moves with the dashboard so the two never look out of step. Nothing inside `initialize()` changed, so there is nothing to re-register.
4. The footer should read v2.1.3.

## For the technically inclined

The link builder tolerates a partial or pretty-printed paste, because a browser pretty-prints JSON and people reasonably copy a selection rather than the whole file. It parses the paste as JSON where it can and falls back to extracting the two fields by pattern where it cannot — but it always names the fields it wants, so tolerance in the input never becomes ambiguity in the output.

503 tests, and seven deliberate breaks of this code, all caught. One of those breaks survived the first sweep: an assertion checked that a variable name and a message string were present in the Diagnostics source, and both still appeared with the branch hard-wired off. That is the third time in this release series that a test asserting text was present agreed with a feature that had been disabled. Assertions over source now pin the binding rather than the occurrence.
