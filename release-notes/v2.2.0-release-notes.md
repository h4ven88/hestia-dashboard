# Hestia v2.2.0

Released 2026-10-03.

This release closes a set of security gaps left behind when v2.0.0 encrypted the
cloud record, and repairs the household-splitting problems that same release
caused. Those two things turned out to be one piece of work: the gaps and the
fallout both live in the path between a device, its hub, and the cloud record.

**Update both halves.** Re-paste `HestiaDashboard.groovy`, then open the app and
click **⬇ Update Dashboard File**. `initialize()` did not change in this
release, so you do **not** need to click Done.

---

## Security

### A neighbour could set off your smoke alarm

The most serious issue, and it needed two unauthenticated endpoints to compose.

`/api/config/discover` returned the record's plaintext half to anyone, which
included a labelled inventory of your contact sensors, motion sensors, smoke
detectors and door locks. `/api/push/webhook`, the endpoint Maker API posts
device events to, accepted those events with no credential at all. And `smoke`
is on the list of categories that deliberately bypass the armed-only gate,
because a fire matters whether or not the house is armed.

Put together: anyone sharing your public IP address could read your smoke
detector's device id and then post a fabricated "smoke detected" event for it.
Every registered device in the household would receive **"Smoke / CO Alert"**,
at any hour, repeatably. The same trick could hold the Activity Log's motion
cooldown open so real motion was never recorded.

Under CGNAT, "anyone sharing your public IP address" is strangers.

Both halves are closed. The webhook now carries a capability in its URL, and the
record's plaintext half is served only to a caller that can prove it belongs to
the household.

### Four endpoints that were never authorised

v2.0.0 secured the config endpoint and the two endpoints the hub calls, because
the hub has the Maker API token to hand. The endpoints the *browser* calls were
left on the original assumption that sharing a public IP means sharing a
household.

| Endpoint | What it allowed |
|---|---|
| `push/subscribe` (PUT) | adding a device to your push list, and receiving your notifications |
| `push/subscribe` (DELETE) | removing your devices, so your alarms go quiet |
| `activity` (GET) | reading when your doors opened and when the house was disarmed |
| `activity/report` (POST) | writing fabricated entries into your Activity Log |

The first three now require proof of the household. The fourth had no callers at
all and has been deleted rather than secured.

The push roster also gained a 32-device ceiling. Without one, a flooded list
pushed real notification delivery past Cloudflare's per-request limit, which
meant a genuine alarm silently failed to send.

### A rotated Maker API token is no longer a lockout

Regenerating your Maker API token in Hubitat used to lock your household out of
its own cloud record permanently, because write authority was proved with that
token and the stored copy could never be updated again.

There is now a third credential that survives rotation: a value stored inside
the encrypted half of the record, so presenting it proves you can decrypt the
record. The backend still holds no decryption path of its own.

This is not retroactive. A household already in that state before this release
is not rescued by it, because its record predates the new credential.

### Smaller items

- A record written before the encrypted format can no longer be used to claim a
  household's slot with a verifier the caller chose.
- Authorisation failures now say **which** credential failed. Previously every
  rejection read as "different Maker API token", including when the real cause
  was a mismatched household key, which sent at least one person down the wrong
  path.
- The record now carries its own expiry, so a locked-out household can be told
  the date it clears rather than being advised to wait.
- Settings → Wall Panel now states that the link contains your household key, not
  just "API credentials". It is enough to read your settings, including PINs and
  camera URLs. Do not post it in a screenshot.

## Household splitting

### One device could re-key your whole household

A device that cannot reach the companion app used to invent its own household
key. That sounds rare and is not: discovering the companion app is blocked by
design when the dashboard is loaded from hestari.com rather than from the hub,
and it also happens whenever the app-id circuit breaker is open.

So one physical device could end up with two different keys across its two
addresses. Whichever one saved last re-encrypted the shared record, and every
other device in the house could no longer read its own settings.

Three guards now close this, at three different levels:

1. A device that knows a companion app exists treats "cannot reach it" as
   exactly that, and waits rather than inventing a key.
2. A device that finds a record it cannot read refuses to mint over it.
3. **The hub refuses to replace a household's key with a different one.** This is
   the one that matters most. Every client passes through it, including older
   clients that will never be updated.

Importing a settings file was a live route into the same failure, because the
export deliberately does not contain your household key. That route is closed
too.

### A device with the wrong key now fixes itself

If a device holds a key that does not open the household's record, it will try
keys that have opened it before and adopt the one that works. The record decides,
which is a stronger test than anything a device can assert about itself.

### You can enter a household key on a device that is working

Previously the only place to type one was the recovery screen, which only
appears on a device with no settings at all. Diagnostics told working devices to
use it anyway. The only way people could find to reach it was to wipe a device
and start over, which minted a new key and took the rest of the household down.

Settings → Diagnostics now has a **Household key** box. It checks the key
against your real record before storing anything, so a wrong value cannot make
things worse.

### Diagnostics tells the truth

- Opening the dashboard from your hub's own address means cloud requests go to
  the hub, which has nothing to answer them with. This was reported as "could not
  reach the hestari.com backend", which named a service the request never went
  near. It now names the real cause, says what is genuinely unavailable from that
  address, and says what is unaffected: your hub still fires reminders, and push
  still reaches devices that are already registered.
- When a write is rejected as unauthorised, Diagnostics now warns that **alarm
  and arm/disarm notifications are being refused**, while door, window and motion
  notifications keep arriving. That combination is easy to mistake for a healthy
  system.
- When a record cannot be read, Diagnostics now compares the devices named in it
  against your own and says whether it is yours. That decides whether waiting
  helps.

## Compatibility

**Device-event notifications keep working during a changeover period.** Only the
browser can register the new webhook URL, so enforcing it immediately would have
silently stopped notifications for any household that does not open a dashboard,
which is exactly the household that relies on push most.

Uncapped webhook posts are therefore still accepted, **until 2026-11-30**. Each
household stops accepting them the moment it registers the new URL, which happens
by itself the first time a dashboard is opened after this update. After that date
the old form stops working everywhere.

The same applies to records still in the pre-v2.0.0 format: they are still read
during this window so that households finish migrating rather than losing push on
the day they update.

**If you have not opened your dashboard since updating, open it once.** That one
visit registers the new webhook, publishes the new recovery credential, and
closes both windows for your household.
