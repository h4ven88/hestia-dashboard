# Hestia v2.1.4 Release Notes

**Release Date:** 2026-09-30

Entering your household key now actually restores your settings. Until this release it handed you the setup wizard instead, and finishing that wizard replaced your household.

---

## Entering your key led back into the bug it was meant to fix

v2.1.2 and v2.1.3 added a way to recover a device that had lost its household key: paste the key, and the device can read your settings again. The key half worked. The restore half did not.

**What went wrong.** After the key was accepted, boot fetched your settings from the cloud and decrypted them correctly. Then a separate check decided whether those settings could be trusted, and that check only knew two things: "is this the hub this device already uses" and "has this device accepted this household before". Both of those live in browser storage, and anyone recovering a device has usually just cleared it.

So the settings were read successfully and then discarded as untrusted, and the setup wizard appeared. Completing it rebuilt rooms from scratch, created a **new** household key, and overwrote the household record — locking out every other device, exactly as in the v2.0.2 bug this recovery path exists to fix.

**The check never looked at the household key itself**, which is the strongest evidence there is. It was written before household keys existed and was never taught about them.

**What it does now.** If your settings decrypt with the key your device holds, that is proof they are yours, and they are applied. No wizard, no prompt, nothing to confirm. This is safe for a specific reason: the record is sealed with authenticated encryption, so it can only be opened by someone holding your key. Somebody else on your internet connection cannot produce a record that opens with it.

The older, weaker records are deliberately excluded from this. Those are encrypted with a key derived from your public address plus a value published in this project's source, which anyone sharing that address can recompute. Reading one proves nothing about whose it is, so it still goes through the confirmation prompt exactly as before.

## If this already happened to you

Your other devices are now locked out, because finishing the wizard changed the household key.

1. Open Hestia on the device where you completed setup. That device holds the current key.
2. Go to **Settings → Wall Panel** and copy the link.
3. Open that link on each other device.

The link carries the key across. Check that the device you copy from does **not** show the warning that the link carries no household key; if it does, that device has no key either, and the recovery screen's **Build my link** flow is the way back.

## Updating

1. **The dashboard.** On hestari.com, reload. That is all this release changes.
2. **Companion app.** Paste `HestiaDashboard.groovy` over Apps Code → Save, then open the Hestia app and click **⬇ Update Dashboard File**.
3. **Clicking Done is not required.** The companion app's code is unchanged; its version moves with the dashboard so the two never look out of step.
4. The footer should read v2.1.4.

## For the technically inclined

The vouch is scoped to the household it was derived from, not to "a successful decrypt happened recently". It is cleared at the start of every discovery call, set only on the household-key path, and compared against the identity of the record it came from, so it cannot vouch for a different configuration presented afterwards.

511 tests. Four of five deliberate breaks of this logic were caught, including restoring the original bug and two that would have let a forgeable record be trusted automatically. The fifth was equivalent to the original code and encodes no behaviour: it moves an assignment above a decryption that, when it fails, returns before the assignment is ever read.

One of those runs also found that a second test suite crashed rather than failing, because it built its own sandbox around this function and did not know about the new variable. The suite runner reported it as unreadable rather than passing, which is the guard added after a deleted suite once reported green.
